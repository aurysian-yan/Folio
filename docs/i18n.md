# 国际化与翻译管理

Folio 的三套客户端共用同一套界面字段：

- macOS 原生客户端（SwiftUI，`apps/macos`）
- Windows/Linux 桌面客户端（React + Tauri，`apps/desktop-ui`）
- 移动端概念验证（React Native + Expo，`experiments/mobile`）

所有语言的源文案都只维护在仓库根目录的 `locales/` 中，客户端在运行时直接读取
同一份字段。这样同一个界面概念（例如“收藏夹”“可变字体”“已安装”）在三端只会
登记一次，避免各客户端各自维护一份字符串表而产生重复字段。

```text
locales/
├── zh-CN.json     # 源语言（简体中文），也是新增字段的入口
└── en.json        # 英文
```

## 字段结构

字段使用语义化命名空间，公共词汇提取到共享命名空间，只有确属单一平台的概念
才放入平台命名空间：

| 命名空间 | 说明 |
| --- | --- |
| `common.*` | 通用动作与名词（取消、保存、搜索、名称、颜色…） |
| `font.*` `fontState.*` `fontCategory.*` `fontFeature.*` `fontConflict.*` `weight.*` `color.*` `collectionIcon.*` `libraryView.*` | 字体领域词汇，三端共用 |
| `library.*` `filters.*` `collection.*` `preview.*` `inspector.*` `settings.*` `cloud.*` `online.*` `script.*` `storage.*` | 各功能区块的共享文案 |
| `import.*` `health.*` | 导入与健康检查 |
| `desktop.*` `mobile.*` `macos.*` | 仅在对应平台出现的文案 |

书写约定：

- 占位符使用 `{{name}}`，例如 `"familyCount": "{{count}} 个字族"`。
- 复数字段在英文中通过 `_one` / `_other` 后缀表达，源语言只保留基础键：
  ```json
  // zh-CN.json
  "familyCount": "{{count}} 个字族"
  // en.json
  "familyCount_one": "{{count}} family",
  "familyCount": "{{count}} families"
  ```
  客户端调用时传入 `count` 即可，`i18next` 与 macOS 的 `stringsdict` 会各自选择
  正确形式。
- 标点符号（`·`、`，`、`｜` 等）写进译文，不要在代码里拼接。

## 三端接入方式

| 平台 | 资源来源 | 运行时入口 |
| --- | --- | --- |
| 桌面端 | 直接引用 `locales/*.json` | `apps/desktop-ui/src/i18n/index.ts`（i18next + react-i18next，默认跟随系统语言，可在设置中切换并持久化） |
| 移动端 | 直接引用 `locales/*.json`（Metro `watchFolders` 放开上级目录） | `experiments/mobile/src/i18n/index.ts`（跟随系统语言） |
| macOS | 构建期由 `tools/i18n/build.mjs` 生成 `.lproj` 资源 | `apps/macos/Folio/Localization.swift` 的 `enum L` |

macOS 的 `.lproj/Localizable.strings`、`Localizable.stringsdict` 与
`InfoPlist.strings` 在 Xcode 构建阶段（`Generate Localizations`）生成到应用
bundle，不进入版本库，因此不存在第二份需要手工同步的文案。

Swift 调用示例：

```swift
Text(L.text("common.cancel"))
Text(L.format("macos.familyMenu", family.name, String(family.styles.count)))
Text(L.plural("library.familyCount", count))
```

## 常用命令

```sh
pnpm i18n:validate   # 校验重复键、各语言键集合与占位符一致性
pnpm i18n:build      # 本地生成 macOS 本地化资源（默认输出到 apps/macos/Folio/Resources）
pnpm i18n:unused     # 报告没有被任何客户端引用的字段，便于精简
pnpm i18n:push       # 上传 locales/zh-CN.json 作为源文案
pnpm i18n:pull       # 拉取译文并写回 locales/<locale>.json
```

## 翻译管理平台

翻译托管使用 **Crowdin**，配置见仓库根目录 `crowdin.yml`。选择理由：

- Crowdin 是成熟的商业翻译管理平台，支持审校、术语表、翻译记忆与 JSON 格式。
- 仓库采用 AGPL-3.0 开源许可，可申请 Crowdin 的开源免费方案，不需要自建
  服务器，也不产生额外费用。
- 通过本地 CLI 与仓库中的 `locales/` 同步，字段只有一份，三端共用。

接入步骤：

1. 在 Crowdin 创建项目并申请开源方案，把源语言设为简体中文（zh-CN），
   添加英文（en）。
2. 在项目设置中把 `{{...}}` 登记为占位符格式（Custom placeholders），避免翻译
   时被改动。
3. 本地导出凭据后执行同步：

   ```sh
   export CROWDIN_PROJECT_ID=<项目 ID>
   export CROWDIN_PERSONAL_TOKEN=<个人令牌>
   pnpm i18n:push
   pnpm i18n:pull
   ```

4. 译文拉回后运行 `pnpm i18n:validate` 与对应平台的类型检查/构建。

凭据只通过环境变量提供，不写入仓库；`crowdin.yml` 中使用的是变量名。

## 已知限制

- 筛选面板中的部分选项标签由 Rust 接口直接返回中文（例如 `folio-ffi` 的
  `facet_count` 会生成「字重 400」「汉字」「多字款」等 `label`）。三套客户端目前
  直接显示这些后端标签，因此英文界面下这些筛选标签仍为中文。后续应由后端改为
  返回稳定的取值，客户端再用 `font.*` / `script.*` 等共享字段本地化。

## 精简字段

`pnpm i18n:unused` 会列出没有被任何客户端引用的字段。确认不再需要后可以删除，
避免翻译平台为不会展示的文案消耗翻译量；`common.appName` 与
`macos.fontDocumentType` 由 Swift 资源生成脚本使用，不在客户端源码中引用，需要
保留。

## 新增或修改文案

1. 在 `locales/zh-CN.json` 增加或修改字段，尽量复用已有共享键。
2. 在 `locales/en.json` 补上同名键（复数字段补 `_one`）。
3. 运行 `pnpm i18n:validate`。
4. 在客户端代码中用对应键调用；macOS 侧会自动在下次构建生成资源。
